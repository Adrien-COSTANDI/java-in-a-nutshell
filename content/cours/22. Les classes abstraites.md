On a vu l'[[18. Les objets (Partie 2)#Héritage|héritage]] avec `extends`. Mais parfois, on veut créer une classe qui sert de **modèle** sans pouvoir être instanciée directement. C'est là qu'interviennent les classes abstraites. Un concept un peu abstrait, justement, mais très pratique !

## Qu'est-ce qu'une classe abstraite ?

Une classe abstraite, c'est une classe qui **ne peut pas être instanciée**. Elle sert uniquement de base pour d'autres classes. C'est un peu comme un plan d'architecte : on ne peut pas habiter dans un plan, mais toutes les maisons construites à partir de lui en découlent.

```java
public abstract class Animal {
  protected String name;

  public Animal(String name) {
    this.name = name;
  }

  public void sleep() {
    IO.println(name + " dort.");
  }

  public abstract void makeSound(); // pas d'implémentation !
}
```

Le mot clé `abstract` sur la classe signifie qu'on ne peut pas faire `new Animal("Toto")`. Le mot clé `abstract` sur la méthode signifie que les sous-classes **doivent obligatoirement** fournir une implémentation. La classe mère impose le contrat, les filles le remplissent.

```java
public class Dog extends Animal {
  public Dog(String name) {
    super(name);
  }

  @Override
  public void makeSound() {
    IO.println(name + " aboie !");
  }
}

public class Cat extends Animal {
  public Cat(String name) {
    super(name);
  }

  @Override
  public void makeSound() {
    IO.println(name + " miaule !");
  }
}
```

Maintenant, on peut utiliser le polymorphisme :

```java
void main() {
  Animal[] animals = {
    new Dog("Rex"),
    new Cat("Misty")
  };

  for (Animal a : animals) {
    a.makeSound(); // chaque animal fait son propre bruit
  }
}
```

La boucle parcourt des `Animal`, mais chaque appel à `makeSound()` exécute la version du type réel : le chien aboie, le chat miaule. C'est ça, le **polymorphisme** : un même appel, des comportements différents selon l'objet !

## Méthode abstraite vs concrète

- **Méthode concrète** : a un corps, du code entre les accolades. Les sous-classes peuvent la redéfinir ou non.
- **Méthode abstraite** : pas de corps, juste `;` à la fin. Les sous-classes **doivent** la redéfinir.

```java
public abstract class Shape {
  public abstract double area();      // abstraite — doit être implémentée

  public void display() {             // concrète — peut être héritée telle quelle
    IO.println("Aire : " + area());
  }
}
```

## Pourquoi utiliser une classe abstraite ?

### 1. Factoriser du code commun

Si plusieurs classes partagent des attributs et des méthodes, on les met dans une classe abstraite pour éviter la duplication. Pas question de copier-coller du code partout !

```java
public abstract class Employee {
  protected String name;
  protected double baseSalary;

  public Employee(String name, double baseSalary) {
    this.name = name;
    this.baseSalary = baseSalary;
  }

  public abstract double calculatePay();

  public void displayInfo() {
    IO.println(name + " : " + calculatePay() + "€");
  }
}

public class Developer extends Employee {
  private int projectCount;

  public Developer(String name, double baseSalary, int projectCount) {
    super(name, baseSalary);
    this.projectCount = projectCount;
  }

  @Override
  public double calculatePay() {
    return baseSalary + projectCount * 500;
  }
}

public class Manager extends Employee {
  private int teamSize;

  public Manager(String name, double baseSalary, int teamSize) {
    super(name, baseSalary);
    this.teamSize = teamSize;
  }

  @Override
  public double calculatePay() {
    return baseSalary + teamSize * 1000;
  }
}
```

Le nom, le salaire de base et l'affichage sont partagés. Chaque type d'employé ne fournit que sa propre logique de calcul. Propre, non ?

### 2. Forcer un contrat

En mettant des méthodes abstraites, on oblige toutes les sous-classes à les implémenter. C'est une forme de **contrat** que la classe mère impose à ses filles. Si un développeur oublie d'implémenter `calculatePay()`, le compilateur le refusera : impossible de créer une sous-classe incomplète !

## Différence avec l'interface

Les classes abstraites et les [[23. Les interfaces|interfaces]] sont souvent confondues. Voici la différence :

| Classe abstraite | Interface |
|:---|:---|
| Peut avoir des attributs (même `private`) | Attributs = `public static final` uniquement |
| Peut avoir des constructeurs | Pas de constructeurs |
| Méthodes concrètes ET abstraites | Méthodes abstraites (ou `default`/`static` depuis Java 8) |
| Une classe ne peut en étendre qu'une seule | Une classe peut en implémenter plusieurs |

En règle générale :
- Si vous avez du **code en commun** (attributs, méthodes concrètes) → classe abstraite
- Si vous définissez juste un **contrat** (comportement sans code) → interface

On voit tout de suite que les deux outils se complètent. Et devinez quoi, les interfaces sont notre prochain arrêt !
