Certains objets peuvent être modifiés après leur création, d'autres non. On parle d'**objets mutables** et **immuables**. Cette petite distinction a de grandes conséquences : elle influence la fiabilité de votre code, vos performances et votre tranquillité d'esprit !

## Objet immutable (immuable)

Un objet **immuable** est un objet dont l'état ne peut pas changer après sa création.

```java
String s = "Hello";
s = s + " World"; // on crée une NOUVELLE String, on ne modifie pas l'originale
```

`String` est la classe immuable la plus connue en Java. Toutes les méthodes comme `toUpperCase()`, `substring()`, `concat()` retournent une **nouvelle** chaîne sans modifier l'originale. C'est pour ça que vos `String` ne se font jamais "trahir" : personne ne peut les modifier en douce !

```java
public class ImmutablePerson {
  private final String firstName;
  private final String lastName;
  private final int age;

  public ImmutablePerson(String firstName, String lastName, int age) {
    this.firstName = firstName;
    this.lastName = lastName;
    this.age = age;
  }

  public String getFirstName() { return firstName; }
  public String getLastName() { return lastName; }
  public int getAge() { return age; }
}
```

Des attributs `final`, pas de setters : une fois l'objet construit, impossible de le changer. Et devinez quoi ? Avec les [[24. Les records|records]], l'immuabilité est automatique :

```java
public record Person(String firstName, String lastName, int age) { }
// Immutable par défaut !
```

### Propriétés d'une classe immuable

Pour rendre une classe immuable :
1. Tous les attributs sont `final`
2. Pas de setters
3. La classe est `final` (ou les constructeurs sont privés) pour éviter la redéfinition
4. Si un attribut est un objet mutable, on ne partage pas sa référence (on fait une copie défensive)

Le point 4 est le plus délicat. Prenons une `List`, qui elle est mutable :

```java
public final class Team {
  private final String name;
  private final List<String> members; // List est mutable !

  public Team(String name, List<String> members) {
    this.name = name;
    this.members = List.copyOf(members); // copie immuable !
  }

  public List<String> getMembers() {
    return members; // déjà immuable grâce à List.copyOf
  }
}
```

On copie la liste à l'entrée avec `List.copyOf` pour ne pas partager la référence du monde extérieur. Sans ça, un `members.add(...)` externe modifierait notre équipe sans que nous le sachions !

### Pourquoi l'immuabilité ?

- **Pas d'effets de bord** — on peut passer un objet immuable partout sans craindre qu'il soit modifié
- **Thread-safe** — pas besoin de synchronisation, aucun thread ne peut le modifier
- **Moins de bugs** — l'état ne change pas, donc moins de surprises

En résumé : l'immuabilité, c'est la tranquillité. Un objet qu'on peut passer à dix méthodes différentes sans jamais se demander s'il va ressortir intact !

## Objet mutable

Un objet mutable peut être modifié après sa création.

```java
public class MutablePerson {
  private String name;
  private int age;

  public MutablePerson(String name, int age) {
    this.name = name;
    this.age = age;
  }

  public void setName(String name) { this.name = name; }
  public void setAge(int age) { this.age = age; }
  public void birthday() { this.age++; }
}
```

```java
void main() {
  MutablePerson p = new MutablePerson("Alice", 29);
  p.birthday(); // l'objet est modifié sur place
  IO.println(p.getAge()); // 30
}
```

Ici, l'objet vit et change : il vieillit, on modifie son nom. C'est pratique, mais ça peut aussi causer des problèmes :

```java
void main() {
  List<String> names = new ArrayList<>();
  names.add("Alice");
  processList(names);
  IO.println(names); // modifié sans qu'on le demande !
}

void processList(List<String> list) {
  list.add("Bob"); // effet de bord !
}
```

Regardez bien : la méthode `processList` modifie la liste sans prévenir. Le `main` s'en aperçoit après coup — et imaginez ça dans un gros programme : c'est ce qu'on appelle un **effet de bord**, et il est souvent la source de bugs sournois !

## Piège : références partagées

C'est le danger numéro un des objets mutables :

```java
public class Person {
  private List<String> hobbies;

  public Person(List<String> hobbies) {
    this.hobbies = hobbies; // attention : on partage la référence !
  }

  public List<String> getHobbies() {
    return hobbies; // attention : on donne accès à notre interne !
  }
}

void main() {
  List<String> hobbies = new ArrayList<>();
  Person p = new Person(hobbies);

  hobbies.add("Hacking"); // on modifie l'objet de l'extérieur !
  // p est maintenant contaminé
}
```

La personne a été "contaminée" par le monde extérieur : on a ajouté un hobby sans passer par elle. Le problème, c'est qu'on a **partagé la référence** au lieu de la protéger. Solution : **copies défensives** :

```java
public Person(List<String> hobbies) {
  this.hobbies = new ArrayList<>(hobbies); // copie
}

public List<String> getHobbies() {
  return Collections.unmodifiableList(hobbies); // version non modifiable
}
```

On copie à l'entrée, on protège à la sortie. La personne garde le contrôle total de ses données !

## Immuable vs non modifiable

- **Immuable** : l'objet ne peut **vraiment pas** être modifié (comme `String`)
- **Non modifiable** : l'objet est mutable en interne mais n'expose pas de moyen de le modifier (comme `Collections.unmodifiableList`)

```java
List<String> original = new ArrayList<>();
original.add("A");
List<String> view = Collections.unmodifiableList(original);
// view.add("B"); // exception !
original.add("B"); // mais on peut encore modifier original, et view reflète le changement
```

Subtile distinction : `view` refuse toute modification directe, mais si on modifie `original`, la vue reflète le changement. C'est une protection, pas une vraie immuabilité !

## Dans la pratique

| Classe | Mutable ? |
|:---|:---|
| `String` | Non |
| `StringBuilder` | Oui |
| `Integer`, `Long`, etc. | Non (value types) |
| `ArrayList`, `HashMap` | Oui |
| `Collections.unmodifiableList(…)` | Non modifiable |
| `List.of(…)` | Non modifiable |
| `Record` | Non |

Règle générale : **préférez l'immuabilité** quand c'est possible. Si vous devez être mutable, soyez conscient des conséquences et protégez vos données avec des copies défensives. Votre futur vous (et vos collègues) vous remercieront !

En parlant de valeurs qui se passent et se transforment, on change de paradigme avec [[31. La programmation fonctionnelle|la programmation fonctionnelle]] !
