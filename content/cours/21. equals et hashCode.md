On a déjà vu que toutes les classes héritent de [[18. Les objets (Partie 2)#La classe `Object`|Object]] et que `toString()` permet de représenter un objet en texte. Mais `Object` fournit deux autres méthodes essentielles : `equals()` et `hashCode()`. Ce sont elles qui décident de quand deux objets sont "les mêmes", et elles vous éviteront des heures de debugging si vous les comprenez bien !

## equals()

### Pourquoi comparer des objets avec equals et pas == ?

L'opérateur `==` compare les **références**, pas le contenu des objets. Autrement dit, il se demande "est-ce le même objet au même endroit en mémoire ?", pas "ces deux objets ont-ils les mêmes valeurs ?".

```java
void main() {
  Person p1 = new Person("Alice", 30);
  Person p2 = new Person("Alice", 30);
  Person p3 = p1;

  IO.println(p1 == p2);  // false (pas le même objet dans le tas)
  IO.println(p1 == p3);  // true (même référence)
  IO.println(p1.equals(p2)); // dépend de l'implémentation d'equals
}
```

`p1` et `p2` sont deux objets distincts dans le [[17. La mémoire en Java#Le tas (heap)|tas]], même s'ils contiennent les mêmes valeurs. `==` regarde si c'est la **même adresse mémoire**, pas si le contenu est équivalent. C'est le piège n°1 en Java, et il vaut mieux le comprendre une bonne fois pour toutes !

### Redéfinir equals

Par défaut, `equals()` dans `Object` fait la même chose que `==` (comparaison de références). Pour comparer le **contenu**, il faut le redéfinir.

```java
public class Person {
  private String firstName;
  private String lastName;
  private int age;

  // constructeur, getters, etc.

  @Override
  public boolean equals(Object obj) {
    if (this == obj) return true;               // même référence
    if (obj == null) return false;              // pas de comparaison avec null
    if (getClass() != obj.getClass()) return false; // pas le même type

    Person other = (Person) obj;                // cast vers Person
    return age == other.age
        && Objects.equals(firstName, other.firstName)
        && Objects.equals(lastName, other.lastName);
  }
}
```

On procède par petites vérifications défensives : d'abord la référence, puis `null`, puis le type, et enfin on compare chaque champ un à un. `Objects.equals` est l'outil idéal pour comparer des champs qui peuvent être `null` sans risquer la `NullPointerException`.

### Le contrat d'equals

Il existe des règles à respecter pour qu'une implémentation d'`equals` soit correcte :
- **Réflexivité** : `x.equals(x)` est toujours `true`
- **Symétrie** : si `x.equals(y)` alors `y.equals(x)`
- **Transitivité** : si `x.equals(y)` et `y.equals(z)` alors `x.equals(z)`
- **Consistance** : plusieurs appels donnent le même résultat si l'objet n'est pas modifié
- `x.equals(null)` doit retourner `false`

C'est le genre de contrat qu'on ne doit pas casser, sous peine de voir des collections se comporter bizarrement (on y revient dans une seconde !).

## hashCode()

### À quoi ça sert ?

`hashCode()` retourne un `int` qui représente l'objet. C'est utilisé par les structures de données comme `HashMap`, `HashSet`, etc. (on les verra dans [[29. Les collections]]). Ces structures se servent du hashCode pour ranger les objets dans des cases et les retrouver très vite.

### Le contrat entre equals et hashCode

La règle d'or : **si deux objets sont equals, ils doivent avoir le même hashCode**. L'inverse n'est pas vrai (deux objets différents peuvent avoir le même hashCode, c'est une **collision**).

```java
public class Person {

  @Override
  public int hashCode() {
    return Objects.hash(firstName, lastName, age);
  }
}
```

`Objects.hash()` est une méthode utilitaire qui calcule un hashCode à partir des valeurs données. Simple et efficace !

### Exemple complet

Allez, on rassemble tout dans une classe complète, c'est plus parlant :

```java
import java.util.Objects;

public class Person {
  private String firstName;
  private String lastName;
  private int age;

  public Person(String firstName, String lastName, int age) {
    this.firstName = firstName;
    this.lastName = lastName;
    this.age = age;
  }

  @Override
  public boolean equals(Object obj) {
    if (this == obj) return true;
    if (obj == null || getClass() != obj.getClass()) return false;
    Person other = (Person) obj;
    return age == other.age
        && Objects.equals(firstName, other.firstName)
        && Objects.equals(lastName, other.lastName);
  }

  @Override
  public int hashCode() {
    return Objects.hash(firstName, lastName, age);
  }

  @Override
  public String toString() {
    return firstName + " " + lastName + " (" + age + " ans)";
  }
}
```

### Quand les redéfinir ?

**Toujours** les redéfinir **ensemble** si vous comptez utiliser vos objets dans des collections comme `HashSet` ou `HashMap`, ou si l'égalité de contenu a un sens pour votre classe.

Si vous ne les redéfinissez pas :
- deux objets identiques seront considérés comme différents par les collections
- votre `HashSet` pourrait contenir des "doublons" (catastrophe !)

Imaginez : un `HashSet` qui laisse entrer deux fois la même personne parce qu'il compare les références... C'est le genre de bug sournois qui vous fait perdre une après-midi. Évitez-le en redéfinissant `equals` et `hashCode` ensemble, toujours ensemble !

### Avec les Records

Bonne nouvelle : avec les [[24. Les records|records]], `equals()` et `hashCode()` sont **automatiquement générés** par le compilateur. C'est un des grands avantages des records !

```java
public record Person(String firstName, String lastName, int age) { }
// equals et hashCode déjà corrects !
```

Fini le boilerplate : une ligne suffit, et tout est juste. Décidément, les records vont vite devenir vos amis !
