On a déjà utilisé les génériques sans le savoir dans [[29. Les collections]] avec `List<String>` ou `ArrayList<String>`. Il est temps de comprendre comment ça fonctionne. Et croyez-moi, une fois ce mécanisme compris, vous verrez le code Java avec un autre œil !

## Pourquoi les génériques ?

Avant Java 5, on devait caster à tout va et on pouvait mettre n'importe quoi dans une liste. Et ça, c'était l'enfer :

```java
// Java 1.4 — l'enfer
List list = new ArrayList();
list.add("Hello");
list.add(42);
String s = (String) list.get(0); // cast obligatoire
String t = (String) list.get(1); // ClassCastException à l'exécution !
```

Le problème : la liste ne sait pas ce qu'elle contient. On ajoute un `Integer` à côté d'un `String`, et le premier cast qui passe mal fait exploser le programme **à l'exécution**. Le compilateur ne nous a rien dit, et c'est bien le problème !

Avec les génériques, on précise le type dès la déclaration, et le compilateur vérifie tout :

```java
List<String> list = new ArrayList<>();
list.add("Hello");
// list.add(42);       // erreur de compilation, ouf !
String s = list.get(0);  // pas besoin de cast
```

La sécurité est remontée **à la compilation**. L'erreur apparaît immédiatement, dans votre IDE, avec une jolie ligne rouge, au lieu de surgir en plein vol au pire moment. On ne peut pas demander mieux !

## Définir sa propre classe générique

Les génériques ne concernent pas que les collections. Vous pouvez créer vos propres classes génériques :

```java
public class Box<T> {
  private T value;

  public void set(T value) {
    this.value = value;
  }

  public T get() {
    return value;
  }
}
```

`T` est un **paramètre de type** (type parameter). On le remplace par un vrai type à l'utilisation :

```java
void main() {
  Box<String> stringBox = new Box<>();
  stringBox.set("Coucou");
  IO.println(stringBox.get());

  Box<Integer> intBox = new Box<>();
  intBox.set(42);
  IO.println(intBox.get());
}
```

Une seule classe `Box`, mais qui peut contenir des `String`, des `Integer`, ou n'importe quoi d'autre ! C'est le principe : on écrit la logique **une fois**, et le type est décidé au moment de l'utilisation.

Par convention, les noms de paramètres de type sont une seule lettre majuscule :
- `T` → Type
- `E` → Element (collections)
- `K`, `V` → Key, Value (maps)
- `N` → Number
- `R` → Return type

Ces conventions sont tellement répandues qu'il faut les respecter : un développeur Java qui voit `K` et `V` comprend immédiatement qu'il s'agit d'une paire clé/valeur !

## Méthodes génériques

On peut aussi avoir des méthodes génériques, même dans une classe non générique :

```java
public class Utils {
  public static <T> T identity(T value) {
    return value;
  }

  public static <T> void printArray(T[] array) {
    for (T element : array) {
      IO.println(element);
    }
  }
}
```

```java
void main() {
  String s = Utils.identity("Hello");
  Integer i = Utils.identity(42);

  String[] words = {"A", "B", "C"};
  Utils.printArray(words);
}
```

Le `<T>` avant le type de retour indique que la méthode est générique. Une seule méthode `printArray` qui fonctionne pour des `String[]`, des `Integer[]`, et tout le reste. Élégant, non ?

## Types paramétrés et héritage

Attention, voilà un piège classique, très contre-intuitif :

```java
List<String> strings = new ArrayList<>(); // ok
// List<Object> objects = strings;       // erreur ! contre-intuitif
```

On pourrait se dire "String est un Object, donc List\<String\> devrait être une List\<Object\>". Eh bien non ! Et il y a une excellente raison. Si c'était autorisé :

```java
List<String> strings = new ArrayList<>();
List<Object> objects = strings; // si autorisé
objects.add(42);                 // on ajoute un Integer dans une liste de String !
String s = strings.get(0);       // ClassCastException !
```

On aurait le même problème qu'à l'époque de Java 1.4 : un `Integer` se retrouverait dans une liste de `String`, et tout exploserait à l'exécution. C'est pour ça que les génériques sont **invariants** : `List<String>` n'est pas un sous-type de `List<Object>`, même si `String` est un sous-type de `Object`. (À la différence des tableaux : `String[]` est un sous-type de `Object[]` — ce qui peut causer des erreurs à l'exécution. Encore un point pour les génériques !)

## Bornes (wildcards) : `? extends` et `? super`

Pour plus de flexibilité, on utilise des **wildcards**. C'est ici que les génériques montrent toute leur finesse !

### ? extends T (covariance)

```java
public static double sum(Box<? extends Number> box) {
  Number value = box.get();
  return value.doubleValue();
}
```

On peut lui passer `Box<Integer>`, `Box<Double>`, etc. On peut **lire** depuis la boîte (on est sûr que c'est un `Number`), mais on ne peut pas **écrire** (on ne sait pas quel sous-type exact). Le wildcard `? extends Number` dit : "n'importe quel type qui est un Number ou un de ses descendants".

### ? super T (contravariance)

```java
public static void addNumber(Box<? super Integer> box) {
  box.set(42); // on peut écrire un Integer
}
```

On peut lui passer `Box<Integer>`, `Box<Number>` ou `Box<Object>`. On peut **écrire** un `Integer`, mais on ne sait pas trop ce qu'on va **lire** (au mieux un `Object`). C'est l'exact inverse du cas précédent, et c'est voulu !

### ? (wildcard non borné)

```java
public static void printBox(Box<?> box) {
  Object value = box.get(); // on sait juste que c'est un Object
  IO.println(value);
}
```

Utile quand on a juste besoin d'une fonction utilitaire qui ne dépend pas du type. Pas de borne, pas de lecture précise : on sait juste que c'est un `Object`, et c'est suffisant pour ce qu'on veut faire.

### La règle mnémotechnique

Pour retenir quand utiliser quoi, les Anglais ont un mantra : **PECS** — *Producer Extends, Consumer Super*. Si la méthode **produit** des valeurs (elle les lit), on utilise `? extends` ; si elle **consomme** des valeurs (elle les écrit), on utilise `? super`. Pratique, non ?

## Restrictions des génériques

Quelques limitations à connaître :

```java
public class Example<T> {
  // new T() — interdit !
  // new T[10] — interdit !
  // if (value instanceof T) — interdit !
  // T.class — interdit !

  private T[] array; // déclaration autorisée
  private T value;   // déclaration autorisée
}
```

Pourquoi toutes ces interdictions ? Parce que les génériques sont une fonctionnalité du compilateur. À l'exécution, le type est **effacé** (type erasure) : `Box<String>` et `Box<Integer>` deviennent juste `Box`. La JVM ne sait pas quel type `T` représentait, donc impossible de créer `new T()` ou de faire `instanceof T`. C'est une des rares frustrations du langage, mais on apprend à composer avec !

Les génériques sont un pilier de la programmation moderne en Java : ils donnent de la sécurité au compilateur et de la réutilisabilité à votre code. On continue avec [[24. Les records|un autre raccourci bien pratique]] !
