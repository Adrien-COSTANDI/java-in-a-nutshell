C'est un peu technique, je ne vais pas vous mentir, mais c'est essentiel pour comprendre ce qu'il se passe vraiment quand on crée des objets. ## Le tas (heap) et la pile (stack)

Quand un programme Java s'exécute, sa mémoire est divisée en deux zones principales. Ce sont deux espaces bien distincts, avec chacun son rôle. On va les voir l'un après l'autre.

### La pile (stack)

La pile, c'est l'espace mémoire qui contient :
- les variables locales (y compris les paramètres des méthodes)
- les appels de méthodes en cours d'exécution

Chaque fois qu'une méthode est appelée, un nouveau bloc (on appelle ça un **stack frame**) est ajouté au sommet de la pile. Quand la méthode se termine, ce bloc est retiré. C'est pour ça qu'on parle de "pile" : on empile les appels, puis on les dépile au fur et à mesure.

```java
void main() {
  int x = 5;        // x est sur la pile
  int y = 10;       // y est sur la pile
  int sum = add(x, y); // nouvel appel, nouveau bloc
}

int add(int a, int b) {
  int result = a + b; // a, b, result sont sur la pile
  return result;       // le bloc est retiré
}
```

La pile est rapide mais de taille limitée. Les variables sur la pile sont automatiquement détruites quand la méthode se termine. Pas besoin de "nettoyer" !

### Le tas (heap)

Le tas, c'est l'espace mémoire qui contient **tous les objets** créés avec `{java} new`.

```java
void main() {
  Person p = new Person("Alice", 30); // l'objet Person est dans le tas
}
```

Ici, il y a deux choses :
- la variable `p` (une **référence**) est sur la **pile**
- l'objet `Person` lui-même est dans le **tas**

Contrairement à la pile, le tas est plus grand mais plus lent. Les objets y vivent jusqu'à ce qu'ils ne soient plus utilisés.

### Références vs objets

C'est un point crucial, accrochez-vous : une variable de type objet ne contient **pas** l'objet, mais une **référence** vers l'objet dans le tas. Autrement dit, elle ne contient pas la donnée elle-même, juste l'adresse où la trouver.

```java
Person p1 = new Person("Alice", 30);
Person p2 = p1; // p2 référence le MÊME objet que p1

p2.setName("Bob");
IO.println(p1.getName()); // "Bob" ! p1 a été modifié aussi
```

Si on reprend le parallèle avec les [[8. Variables#Types|types primitifs]] :

```java
int a = 5;
int b = a; // b est une COPIE de a
b = 10;
IO.println(a); // 5, a n'a pas changé
```

Avec les primitifs, la variable **contient** la valeur. Avec les objets, la variable **pointe vers** la valeur. Retenez cette différence, elle explique des comportements qui sembleraient sinon bien mystérieux !

### Passage par valeur

Allez, on complique un peu les choses : en Java, **tout est passé par valeur**. Oui, même les objets ! Mais attention, il faut bien comprendre ce que ça veut dire :

```java
void main() {
  int x = 5;
  modifyPrimitive(x);
  IO.println(x); // 5, pas modifié !

  Person p = new Person("Alice", 30);
  modifyObject(p);
  IO.println(p.getName()); // "Bob" ! l'objet a été modifié
}

void modifyPrimitive(int val) {
  val = 10; // on modifie la COPIE
}

void modifyObject(Person person) {
  person.setName("Bob"); // on modifie l'objet référencé
}
```

Pour les primitifs, la méthode reçoit une **copie** de la valeur. Pour les objets, la méthode reçoit une **copie de la référence**. Les deux variables pointent alors vers le même objet, donc on peut modifier l'objet, mais pas remplacer la référence d'origine. C'est subtil, mais une fois ce mécanisme en tête, plus rien ne vous surprendra !

### Le Garbage Collector

Si les objets restent dans le tas indéfiniment, la mémoire finirait par être saturée. C'est là qu'intervient le **Garbage Collector** (ramasse-miettes, en français).

Le Garbage Collector est un mécanisme automatique de la JVM qui **détruit les objets qui ne sont plus référencés**.

```java
void main() {
  Person p = new Person("Alice", 30);
  p = null; // plus personne ne référence l'objet, il sera nettoyé
}
```

Quand plus aucune variable ne référence un objet, celui-ci devient éligible pour le garbage collection. La JVM s'occupe de libérer la mémoire automatiquement. Pas besoin de `malloc` ou `free` comme en C !

> [!info]
> Contrairement à d'autres langages comme le C, Java gère la mémoire automatiquement. Vous n'avez pas à vous soucier de libérer la mémoire des objets que vous créez. Le Garbage Collector s'en charge pour vous !

### Stack et Heap dans la pratique

Voici un exemple qui montre comment les deux zones interagissent :

```java
void main() {
  String name = "Alice";
  int age = 30;
  Person p = createPerson(name, age);
  IO.println(p);
}

Person createPerson(String name, int age) {
  Person result = new Person(name, age); // Person est dans le tas
  return result; // on retourne la référence
}
```

```
Pile (stack) :
  main() → name ──────┐
           age = 30   │
           p ─────────┤
  createPerson() →    │
    name ─────────────┤
    age = 30          │
    result ───────────┘

Tas (heap) :
  ┌──────────────────────┐
  │ Person "Alice" 30    │←───── référencé par result, puis p
  └──────────────────────┘
```

C'est pour ça qu'on peut retourner un objet créé dans une méthode : la référence est copiée, mais l'objet reste dans le tas. Et comme par magie, une fois la méthode terminée, la pile se vide mais l'objet, lui, continue de vivre dans le tas, prêt à être utilisé.
